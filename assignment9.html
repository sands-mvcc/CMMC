Introduction — Configuration Management & CMMC

Overview

Why Configuration Management Is Critical to Cybersecurity

Every unauthorized or undocumented change to a system's configuration is a potential vulnerability. Attackers exploit misconfigured firewalls, outdated firmware, and default credentials far more often than they exploit novel zero-day exploits. Configuration management is the discipline that ensures every system in the FFSI environment is in a known, approved, and documented state at all times — making unauthorized changes detectable and recoverable.

Why Assessors Review Configuration Management Documentation

During a CMMC Level 2 assessment, a C3PAO assessor will request the Configuration Management Plan and supporting artifacts: baseline configuration records, change request logs, CCB meeting minutes, and configuration audit results. NIST practice 3.4.1 requires organizations to establish and maintain baseline configurations of organizational systems. Practice 3.4.2 requires establishing and enforcing security configuration settings. Without documented baselines, assessors cannot verify that the current system state matches what was approved.

How Unauthorized Changes Create Security Risk

Configuration drift — the gradual divergence of a system's actual configuration from its approved baseline — is one of the most common sources of security gaps in DoD contractor environments. An administrator who modifies a firewall rule without approval, installs unauthorized software, or changes an authentication setting outside of the change control process creates an undocumented attack surface. NIST practice 3.4.3 requires tracking, reviewing, approving, and logging all changes to organizational systems.

Why Baseline Configurations Must Be Documented

A baseline configuration is the "known good" state of a system — the agreed-upon set of settings, software versions, enabled services, and security parameters that have been reviewed and approved. Without a documented baseline, there is no reference point for detecting drift, investigating incidents, or recovering from a breach. CUI cannot be effectively protected on a system whose configuration is unknown. CMMC assessors treat the absence of documented baselines as a significant finding — it undermines the entire security architecture.

How Configuration Management Supports CUI Protection

CUI flows through FFSI systems — from the Contract Management System to file servers to cloud platforms. Configuration management ensures that every system touching CUI has the correct security settings enforced: encryption at rest, MFA requirements, audit logging enabled, unnecessary services disabled, and firmware patched. Without change control, a single misconfiguration can expose CUI without anyone knowing it occurred.

Scenario: FFSI's CIO has tasked the compliance team with reviewing the organization's Configuration Management Plan prior to the CMMC Level 2 assessment. The team has access to the asset inventory, current configuration data, pending change requests, and historical change logs. Your job is to identify configuration items, review baselines, evaluate change requests, and document findings.

Relevant NIST SP 800-171 CM Practices

  • 3.4.1 Establish and maintain baseline configurations and inventories of organizational systems (including hardware, software, firmware, and documentation)
  • 3.4.2 Establish and enforce security configuration settings for information technology products employed in organizational systems
  • 3.4.3 Track, review, approve/disapprove, and log changes to organizational systems
  • 3.4.4 Analyze the security impact of changes prior to implementation
  • 3.4.5 Define, document, approve, and enforce physical and logical access restrictions associated with changes to organizational systems
  • 3.4.6 Employ the principle of least functionality by configuring organizational systems to provide only essential capabilities
  • 3.4.7 Restrict, disable, or prevent the use of nonessential programs, functions, ports, protocols, and services
  • 3.4.8 Apply deny-by-default (blacklisting) approach to prevent use of unauthorized software
  • 3.4.9 Control and monitor user-installed software

Key Terms

Reference Glossary
Configuration Management Plan (CMP)
A formal document describing how an organization identifies, controls, tracks, and audits changes to system configurations — covering baseline establishment, change control procedures, CCB authority, and configuration audit processes.
Configuration Item (CI)
Any hardware, software, firmware, or documentation that is subject to configuration management control. CIs must be individually identified, baselined, and tracked. Systems that process, store, or transmit CUI are always CIs.
Baseline Configuration
The approved, documented, and version-controlled "known good" state of a configuration item — including OS version, patch level, enabled services, security settings, and software inventory. Baselines are the reference point for detecting drift.
Change Request
A formal proposal to modify a configuration item — documenting the requested change, justification, affected systems, risk assessment, rollback plan, and testing requirements. All changes to CUI systems must be formally requested and approved.
Change Control Board (CCB)
A governing body — typically including the CIO, IT Manager, Security Analyst, and Compliance Manager — authorized to review, approve, deny, or defer proposed changes to configuration items. CCB decisions must be documented.
Standard Configuration
An organization-wide approved configuration template — such as a hardened Windows Server image or a standard firewall ruleset — applied consistently across equivalent systems. Standard configurations reduce drift and simplify auditing.
Unauthorized Change
Any modification to a configuration item made without following the defined change control process — including changes made without a change request, without CCB approval, or outside of approved maintenance windows.
Configuration Drift
The gradual divergence of a system's actual configuration from its approved baseline — caused by unauthorized changes, patch inconsistencies, or undocumented maintenance. Drift creates undetected vulnerabilities and fails CMMC audit requirements.
Version Control
The systematic tracking of changes to configuration documents and software — recording what changed, who changed it, when, and why. Version control enables rollback, audit trail reconstruction, and baseline integrity verification.
Asset Inventory
A comprehensive, current record of all organizational assets — hardware, software, and data — including their location, owner, classification, and configuration status. The asset inventory is the source of truth for CMP scoping.
Security Baseline
A minimum set of security configuration requirements applied to a category of systems — based on standards such as CIS Benchmarks, DISA STIGs, or NIST guidelines — that all systems of that type must meet before deployment.
CUI
Controlled Unclassified Information — government-created or -possessed information requiring protection per NIST SP 800-171. Any system that processes, stores, transmits, or protects CUI must be included in the CMP and subject to the highest level of configuration control.
Change Approval
Formal CCB authorization for a proposed change — documented with the approver's name, date, conditions, and any required testing or rollback procedures. Unapproved changes to CUI systems are CMMC findings regardless of their technical merit.
Emergency Change
A change implemented outside of the normal change control process due to an active security threat or critical system failure. Emergency changes still require post-implementation documentation, retroactive CCB review, and baseline update.
Configuration Audit
A periodic review comparing actual system configurations against approved baselines to identify drift, unauthorized changes, or documentation gaps. Configuration audits are evidence that the CMP is actively enforced — assessors request audit records.
