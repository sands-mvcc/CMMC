1. Introduction: The Foundation of Defense Cybersecurity

The NIST and CMMC frameworks govern how unclassified defense information must be protected. The level of required protection depends entirely on the type of data handled.

Federal Contract Information (FCI) vs. Controlled Unclassified Information (CUI)

FCI (Federal Contract Information) is information, not intended for public release, that is provided by or generated for the Government under a contract. It requires basic safeguarding.[1]

CUI (Controlled Unclassified Information) is more sensitive information that requires specific safeguarding or dissemination controls by law or policy. Its loss poses a higher risk.[1]

Key Principle: All CUI in a contractor's possession is considered FCI, but not all FCI is CUI.[1]

CMMC Level Alignment

  • CMMC Level 1 (Foundational): Protects FCI only. Requires 15 basic safeguards (derived from FAR 52.204-21).[2, 3]
  • CMMC Level 2 (Advanced): Protects CUI. Requires all 110 security requirements found in NIST SP 800-171 Revision 2.[2]

2. NIST SP 800-171 Access Control (AC) Domain (3.1.x)

The Access Control domain is the "frontline defense".[4] It defines rules for managing permissions, limiting entry points, and controlling how users and processes interact with systems handling CUI.[5]

The Two Foundational Requirements (Basic Controls)

These two practices are considered basic because their failure would render all other AC security ineffective.[6]

  • 3.1.1 Limit system access to authorized users, processes, or devices. This is about identifying *who* (or *what*) is allowed to get into the system.[7]
  • 3.1.2 Limit system access to the types of transactions and functions that authorized users are permitted to execute. This is about defining *what* the authorized user can actually *do* once they are inside the system.[7]

Interactive Example: Basic vs. Derived Controls

The AC family contains 2 Basic Requirements and 20 Derived Requirements.[7]

Click to see an example of a Derived Control (NIST 3.1.12)

Derived Requirement 3.1.12: Closely monitor and tightly control all access sessions conducted remotely. [7]

This is "derived" because it builds upon the basic control (3.1.1). Once you decide a user is authorized, this requirement mandates *how* you secure their remote session (e.g., monitoring, strict management) due to the higher risk of connecting from outside the perimeter.[7]

Core Themes in AC Controls

The 22 controls in Access Control focus on four key areas [4, 8]:

  1. Authorization: Defining who is allowed access (3.1.1).
  2. Least Privilege: Giving users only the minimum permissions they need (3.1.5).[7]
  3. Session Management: Locking unattended terminals and terminating idle sessions (3.1.10).[7]
  4. Remote & Wireless Access: Using encryption and strict controls for external connections (3.1.13).[7]

3. CMMC Level 1 Access Control Practices (FCI Scope)

CMMC Level 1 is mandatory for organizations handling FCI. It consists of 15 practices across six domains. The Access Control (AC) domain contributes four required practices.[9, 3]

ID Practice L1 Objective
AC.L1-3.1.1 Limit information system access to authorized users, processes, or devices.[9] Ensure access is explicitly limited to defined, approved users and devices.[9]
AC.L1-3.1.2 Limit information system access to the types of transactions and functions that authorized users are permitted to execute.[9] Ensure authorized users can only perform job-required functions (e.g., view a document, but not delete a system file).[9]
AC.L1-3.1.20 Control the use of external information systems in accordance with an organizational policy or procedure.[9] Manage and verify connections to third-party services (e.g., cloud platforms, vendor networks) via a documented policy.[9, 10]
AC.L1-3.1.22 Control the flow of Federal Contract Information (FCI) to and from information systems and networks.[9] Prevent FCI from being posted or processed on publicly accessible systems (e.g., public website, uncontrolled social media).[9]

Policy Implementation Example (AC.L1-3.1.20)

Requirement: Verify and control connections to external information systems.[9]

Technical Example: Connections to external systems are controlled through a firewall and Access Control Lists (ACLs). Access is only granted to pre-authorized external systems, and regular reviews of these external connections are performed.[10]

Documentation Note: L1 compliance requires proving that these controls are managed "in accordance with an organizational policy or procedure".[9]

4. Key Teaching Analogies for Security Concepts

To effectively teach the NIST framework, concepts must be translated into relatable, real-world examples that emphasize policy and process.

Least Privilege Principle (NIST 3.1.5/3.1.6)

Analogy: The Valet Key Concept

When you give a valet your car, they get a "valet key." This key lets them drive and park (their job function), but it won't open the trunk or the glove compartment (restricted functions). For everyday computing, employees must use a standard, non-privileged account (the Valet Key) for routine work. The elevated administrative account (the Master Key) is only reserved for critical, necessary system maintenance, limiting damage if the daily account is compromised.[7]

Remote Access Control (NIST 3.1.12/3.1.13)

Analogy: The Secure Delivery Tunnel

When connecting from home or while traveling, all system access must use an encrypted Virtual Private Network (VPN)—this is the secure tunnel. This tunnel ensures that data transmission is protected by cryptographic keys and routes traffic through the organization's official, secure access control point (like a security checkpoint firewall), preventing direct, risky exposure over the public internet lines.[7]

Separation of Duties (NIST 3.1.4)

Analogy: The Two-Signature Check

This administrative control prevents any single person from performing a high-risk task alone. Just as a sensitive check requires two signatures, critical actions—like modifying system configurations or mass transferring sensitive data—must require approval from two different designated roles. This dramatically reduces the risk of fraud, theft, or catastrophic error without collusion among multiple individuals.[11]
